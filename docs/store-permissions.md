# Chrome Web Store disclosures

> Generated by `pnpm run disclosures` from `docs/store-disclosures.json` and `src/extension/manifest.json`. Edit those, not this file; `pnpm test` fails while this file is stale.

The Misha Browser extension (`src/extension/manifest.json`) asks for the permissions below. The extension has no backend of its own and loads no remote code. Everything it returns goes to the native messaging host on the user's own Mac. The Slack Web API calls and file downloads it makes run inside the user's signed-in Slack page and go to the workspace's address on Slack's domain and to `files.slack.com`. A file upload goes to the upload URL that Slack's Web API answered for it.

The extension does two jobs. Its Slack transport reads new messages in the user's signed-in Slack tab and makes allowlisted Slack Web API calls there for the Misha app. Its tab commands let the browser tools of misha-browser's MCP server (`tab_*`) read and drive the user's tabs.

The docs site explains the same permissions at https://docs.dumdummisha.ai/reference/permissions.

## Single purpose

Misha Browser connects AI agents that run on the user's own Mac to the user's signed-in browser, so they can read pages and carry out the browser actions the user asks for. Misha's Slack transport is one such use: it reads new messages in the user's signed-in Slack tab and makes allowlisted Slack calls there for the Misha app. Both uses reach the browser through one native messaging host on the same Mac.

## Permission justifications

Each section is written to be pasted into the store's justification field for that permission or declaration.

### `nativeMessaging`

**Capability:** Exchanges messages with the native messaging host `misha.browser_bridge`, a program the user installs on their own Mac.

**Justification:** Every request reaches the extension this way: the Misha app's Slack requests and the browser tools' tab commands. Replies, new Slack messages and the extension's status go back the same way. The extension has no backend of its own, so nothing on the Mac could reach it otherwise.

**When data flows:** Automatic. The extension connects when it starts and keeps the connection open. New Slack messages and status go to the listening process as they happen; everything else goes only as the reply to a request.

**Limits:**

- The extension connects to no other native host, and the host's registration lets only this extension start it.
- The host only relays: it passes messages between the extension and processes of the same user on the same Mac (the Misha app, misha-browser's MCP server) and stores none of them.
- With no process listening, the host drops events and status. The extension keeps the events in its pending queue (see `unlimitedStorage`).

### `scripting`

**Capability:** Runs the extension's own bundled functions, and its bundled relay script, in a tab: in the page's own world or in the extension's isolated world.

**Justification:** In a signed-in Slack tab it reads which workspace and user the tab is signed in as, from Slack's saved client state, and makes the allowlisted Slack Web API calls, file downloads and uploads the Misha app asks for. After the extension reloads or updates, it injects the extension's own relay script again into each open Slack tab whose relay the browser has cut off, so capture goes on without reloading the tab (see the content scripts below). It first checks, in the extension's isolated world, that the tab's top document is a page on `https://app.slack.com` with no relay of the running extension, and injects into that document only, never into a page the tab navigated to meanwhile. In the tab a browser tool names, it reads the page as an outline of its visible text and controls (`tab_read`, `tab_find`), finds where a control sits so the tool can click or type into it, reads a form field's state, selects a field's content before typing replaces it, picks an option in a select, reports where the pointer is and whether the page has focus, and waits until the page stops changing after an action.

**When data flows:** On a Slack tab, on a Misha app request, on a browser tool request. On Slack tabs it runs without a request: the relay check when the service worker starts, and the account read for each new message and, while a process listens, whenever the extension reports its status (a listener attaching, a Slack tab loading or closing, a change in a tab's capture or in the queue). Slack calls, downloads and uploads run only when the Misha app asks for one. Page commands run only when a browser tool asks.

**Limits:**

- Everything it runs is part of the extension's package; no code comes from the network or the native host.
- The function that runs in Slack's page returns only the account's ids and the workspace's name, Slack's answers, file bytes or an uploaded file's id, never the session token (see Where Slack's credentials go).
- Slack calls are limited to the Web API methods listed under Slack transport limits.
- Page commands run in the extension's isolated world and read the page's DOM only: not a page's localStorage, Slack's saved session or the cookie store. They skip script and head content and hidden inputs, and give a password field's value only as filled or empty in an outline, or as its length in a field read.

### `alarms`

**Capability:** Wakes the service worker every 30 seconds.

**Justification:** On each alarm the extension reconnects to the native messaging host when the connection is down, for example before the user has installed the host or after it stopped.

**When data flows:** Automatic. The alarm fires on its schedule. It carries no data.

**Limits:**

- While the connection is open, the alarm does nothing.

### `unlimitedStorage`

**Capability:** Exempts the extension's own storage from Chrome's quota and from eviction under storage pressure.

**Justification:** The Slack transport keeps its pending queue in IndexedDB, in the extension's own origin: each new Slack message waits there until the Misha app confirms it saved it, so it survives a service worker or browser restart. Without this permission Chrome may evict the extension's IndexedDB under storage pressure, taking the queued messages and the count of lost ones with it.

**When data flows:** On a Slack tab. A new message is stored as soon as a Slack tab's capture hands it over, and removed when the Misha app acknowledges it, which the app does only after saving it on its side.

**Limits:**

- The queue holds at most 2000 pending events. When it is full, a new event is not stored: it is counted as lost, and the Misha app sees the count in the extension's status.
- An event has no age limit. It stays, and is forwarded again, until the Misha app acknowledges it.
- A stored event holds the account it came to and the message cut down to the fields listed under Slack transport limits.
- Nothing else is stored: the network log, page reads and file transfers stay in memory.

### `tabs`

**Capability:** Reads every open tab's title and URL, and opens, focuses and closes tabs.

**Justification:** `tab_list` lists the open tabs with their titles and URLs, and `tab_open`, `tab_switch` and `tab_close` open, focus and close tabs. The Slack transport uses it to find the open Slack tabs and to report its status again when one loads or closes.

**When data flows:** On a Slack tab, on a browser tool request. Tab titles and URLs leave the extension only in the reply to a browser tool. The Slack transport finds the Slack tabs without a request, and reports for each only the account it is signed in as and how its capture stands.

**Limits:**

- Each structured URL field a tab command returns (a tab's, a page's or a download's) goes through the name- and pattern-based redaction described under `webRequest`, which also removes a URL's userinfo and the grant in Slack's upload URLs.
- An opaque link that grants access under an ordinary name passes unchanged, and a URL that appears in page text or a field value comes back as the page shows it.

### `webRequest`

**Capability:** Observes the fetch and XHR requests every tab sends: method, URL, request body, request headers (cookies included) and the status or error that ends each one.

**Justification:** `tab_network` lists a tab's requests so the model can learn the API a web app calls, and the action tools wait for the requests an action started before they read the page again.

**When data flows:** Automatic. Observation does not wait for a tool: the service worker records every tab's fetch and XHR requests for as long as it runs, whether or not a browser tool is in use. A tab's log leaves the extension only when `tab_network` asks for it.

**Limits:**

- It only observes, and never blocks or changes a request.
- Chrome hands the service worker each request's body and headers, credentials included, so they reach it briefly. It redacts them before it records the request: a body field, query parameter or header named like a token, password, secret, API key, authorization or cookie, and any value shaped like a known token or key, is replaced with `[redacted]`. Matched credential values are replaced before storage; an unrecognized credential can remain.
- The log holds the latest 200 requests per tab and a request body up to 20,000 characters, and never stores response bodies.
- The log lives only in the service worker's memory and is never written to disk. A tab's log goes when the tab closes, and the whole log goes when the service worker stops.
- Requests no tab sent, such as the browser's own or another extension's, are not recorded.

### `downloads`

**Capability:** Searches the browser's download list.

**Justification:** After a browser tool's action, the extension reports the downloads started since the action began (each one's URL, local filename, state, bytes received and any error), so the tool can tell the model that a click downloaded a file, whether it finished, and whether the browser waits for the user to choose where to save it.

**When data flows:** On a browser tool request. After a browser tool's action, never on its own. The extension listens for no download events.

**Limits:**

- The search covers the whole browser, not only the tab the action ran in, so a download started elsewhere in that time is reported too.
- A download's URL goes through the name- and pattern-based redaction described under `webRequest`, which can leave an unrecognized credential.
- The extension only searches the download list. It never starts, opens or deletes a download.

### Host permission `<all_urls>`

**Capability:** Gives the extension access to every site: to script any page, to observe any page's requests with `webRequest`, and to capture the visible part of a tab.

**Justification:** The browser tools work on whatever site the user has open, so the sites cannot be named in advance. The tools read and drive a page with `scripting`, and `tab_screenshot` captures the visible part of a tab.

**When data flows:** Automatic, on a browser tool request. A page's content and screenshots are read only when a browser tool asks. Request observation under `webRequest` runs on every site without a request. The Slack transport's capture in Slack tabs is described under the content scripts below.

**Limits:**

- Page text, control names, ordinary field values and screenshots come back as the page shows them, including any credential the page displays.
- The extension reads the localStorage of no page but Slack's, where its own code reads only the saved client state, and it never reads the cookie store.

### Content script `observer.js`

Declared on `https://app.slack.com/*`, from `document_start`, in the page's own world.

**Capability:** Watches Slack's own real-time socket. It passes each new message to the relay, cut down to the fields the Misha app reads (listed under Slack transport limits), with the account the tab showed when it came, and reports whether the socket is open. It reads the signed-in user's id from Slack's saved client state to key each message.

**Justification:** Slack's web client receives new messages on this socket, and the Misha app needs them as they arrive to answer in Slack. The script runs before Slack's own scripts so it can watch the socket Slack opens.

**When data flows:** On a Slack tab. Without a request, while a Slack tab is open: each new message is passed on as it arrives. Edits and deletions are not passed on.

**Limits:**

- It sends nothing on Slack's socket and never passes on the socket's address, which holds a token.
- Nothing else the page received leaves it, such as file URLs, profiles or message formatting.
- Message text goes on as written, including any credential someone wrote into a message.
- It holds up to 50 messages no relay has taken yet, such as those that come while the extension reloads, in the page's memory, and hands them to the next relay; past that the oldest is dropped.

### Content script `relay.js`

Declared on `https://app.slack.com/*`, from `document_start`, in the extension's isolated world.

**Capability:** Takes a private channel from the observer, checks every message on it against the protocol's shapes, and forwards new messages and the socket's state to the service worker.

**Justification:** A script in the page's own world has no channel to the extension, so the observer needs a partner in the extension's world. Checking what the observer sends keeps anything outside the fixed shapes from reaching the extension.

**When data flows:** On a Slack tab. Without a request, while a Slack tab is open. When the extension reloads or updates, the browser cuts the relay in every open tab off from the extension and loads the manifest's scripts only into pages that load afterwards, so the service worker injects the relay again into each open Slack tab (see `scripting`). There it takes a new channel from the observer, which has kept watching the socket and held any new message that came while no relay ran.

**Limits:**

- It takes a channel only in the top frame of a page on `https://app.slack.com`.
- It passes on nothing that does not match the protocol's shapes, and reports the tab's capture as failed instead.
- Re-attaching works for pages that loaded with this version of the observer. A page still running an older version captures again only once the tab reloads, so upgrading from such a build needs each open Slack tab reloaded once.

The manifest asks for no other permission. Among those it does not request: `debugger`, `cookies`, `webRequestBlocking`, `history`, `bookmarks`.

## Native messaging

The native messaging host is part of this repository (`src/host/`). The user installs it on their own Mac, and the installer registers it as `misha.browser_bridge` with Chrome, Brave or both, naming only this extension's id as allowed to start it. The browser starts the host when the extension connects.

The host relays between the extension and processes of the same user on the same Mac, over a socket in a folder only that user can open: the Misha app and misha-browser's MCP server connect there. Requests come in from those processes and replies go back to the process that asked. New Slack messages and status go to the one process that listens for them, and its acknowledgements go back to the extension. The host keeps none of it.

A request names a method from the extension's fixed set of handlers and carries data as its parameters. It never carries code, and a method the extension does not know is answered with an error.

## Remote code

**Uses remote code:** No.

Every script the extension runs is in its package: the service worker, the two content scripts and the functions it injects with `scripting`, bundled from this repository's source without minification. The extension evaluates no string as code, and its schema library runs in its mode that generates no code. Requests from the native host name a method and carry data, never code. Slack messages and page content are data and never run as script.

## Data usage

- **Personally identifiable information:** Handled. The Slack account's team and user ids and the workspace's name, and what Slack's answers and the pages a browser tool reads hold, such as names and email addresses in Slack profiles.
- **Health information:** Not handled. The extension collects no health data as such. A page a browser tool reads can hold any information; that is declared under Website content.
- **Financial and payment information:** Not handled. The extension collects no financial or payment data as such. A page a browser tool reads can hold any information; that is declared under Website content.
- **Authentication information:** Handled. Slack's session token is read inside the Slack page and used there for the requests the Misha app asks for; it never leaves the page. The network observer receives every request's credentials (tokens, cookies, passwords in request bodies) briefly and redacts the ones it recognizes before recording. A credential a page displays comes back in page reads and screenshots.
- **Personal communications:** Handled. New messages in the user's signed-in Slack tab, the Slack messages and files the Misha app reads or sends through Slack's Web API, and any messages on a page a browser tool reads.
- **Location:** Not handled. The extension reads no location.
- **Web history:** Handled. The open tabs' titles and URLs, returned when a browser tool asks, and the URLs of the fetch and XHR requests tabs send, recorded without a request and kept in memory.
- **User activity:** Handled. Network monitoring: the fetch and XHR requests every tab sends, recorded without a request and kept in memory. The extension records no clicks or keystrokes; it reads the pointer's position in a page only while a browser tool acts there.
- **Website content:** Handled. Page text, controls, form field state, screenshots and the browser's download list, when a browser tool asks, and the bytes of Slack files the Misha app downloads or uploads.

The extension sends data only to the native messaging host on the user's own Mac, which passes it to the Misha app or misha-browser's MCP server there, and makes Slack requests only to Slack. Those local programs give the data to the AI agent working on the user's request; the privacy policy describes where the agent's data goes from there.

- User data is not sold to third parties.
- User data is not used or transferred for purposes unrelated to the single purpose above.
- User data is not used or transferred to determine creditworthiness or for lending purposes.

The use of data the extension handles complies with the Chrome Web Store User Data Policy, including the Limited Use requirements.

## Slack transport limits

- Web API methods the extension calls when the Misha app asks: the reads `auth.test`, `chat.getPermalink`, `conversations.history`, `conversations.info`, `conversations.list`, `conversations.open`, `conversations.replies`, `emoji.list`, `search.messages`, `users.info`, `users.list`, the writes `chat.postMessage`, `chat.update`, `reactions.add`, `reactions.remove`, and for an upload `files.getUploadURLExternal`, `files.completeUploadExternal`.
- Fields a new message keeps when it leaves the page: `type`, `subtype`, `channel`, `channel_type`, `ts`, `user`, `bot_id`, `app_id`, `client_msg_id`, `text`, `thread_ts`, `parent_user_id`, and the id of each file it shares.
- A message is new when it has no subtype or one of `thread_broadcast`, `file_share`.

## Where Slack's credentials go

The function the service worker injects into a Slack tab's own page (`src/service-worker/slack-page.ts`) is the only code that uses the Slack session token. For each call the Misha app asks for, it reads the token from Slack's saved client state, adds it to the request, and sends that request only to the workspace's https address on Slack's domain, with redirects refused. A private file is fetched only from `files.slack.com`, with the browser's cookies and no token, and redirects refused; an upload's bytes go to the upload URL Slack's Web API answered, with neither. It returns the account's ids and the workspace's name, Slack's answer, file bytes or an uploaded file's id. It never returns the token it reads from Slack's saved client state as session state, though a credential someone wrote into a message or a file comes back like any other content. Slack's answers and file bytes go on as Slack sent them, without credential filtering. A command that fails returns a fixed failure code, so no error message can quote what the page holds.

The script that watches Slack's socket reads only the signed-in user's id from the saved state and never passes on the socket's address, which holds a token. It sends only whether the socket is open and new messages cut down to fixed fields, with the account the tab showed. Message text goes on as written. Its partner script and the service worker reject anything outside those shapes. The native host passes messages between the extension and processes on the same Mac and keeps nothing.

The exception is `webRequest`. Chrome gives the service worker the body and headers of every fetch and XHR request a tab sends, Slack's included, so the token in the `token` field of Slack's API calls and the session cookie in the `Cookie` header reach the service worker briefly. It redacts both before it records the request, so `tab_network` shows them as `[redacted]`, and neither is stored or sent to the native host.

What the tab commands can return, on the Slack tab or any other:

- The page commands behind `tab_read`, `tab_find` and field reads run in the extension's isolated world and read the page's DOM. They do not read Slack's saved session, a page's localStorage or the cookie store. They skip script and head content and hidden inputs, and give a password field's value only as filled or empty in an outline, or as its length in a field read. Page text, control names and ordinary field values come back as the page shows them, so a credential the page displays, or one pasted into a Slack message, comes back too.
- `tab_screenshot` returns the pixels the tab shows, including any credential on screen.
- Network requests and returned URLs are redacted by name and pattern only. An opaque credential under an ordinary name, such as the key in a share link, comes back unchanged.

Scripts that already run in the Slack page (Slack's own code, or another extension's) are out of scope: they hold the session themselves. The README's Security section states this threat model.
